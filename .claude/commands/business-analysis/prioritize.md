# 优先级排序命令

使用经过验证的框架系统地确定项目优先级：MoSCoW 用于干系人驱动的分类，Kano 用于客户满意度，加权评分用于多标准决策。

## 参数

- `<项目或上下文>`：要优先排序的项目（内联列表、文件引用或上下文描述）
- `--mode`：优先级排序方法（默认：`moscow`）
  - `moscow`：Must/Should/Could/Won't 分类（约4K tokens）
  - `kano`：客户满意度分类（约5K tokens）
  - `weighted`：多标准加权评分（约6K tokens）
  - `all`：三种方法进行比较（约12K tokens）
- `--output`：输出格式（默认：`both`）
  - `yaml`：结构化 YAML，用于下游处理
  - `markdown`：格式化的 Markdown 表格
  - `both`：两种格式

- `--dir`：输出目录（默认：`docs/analysis/`）

## 执行

### 步骤1：解析参数

从参数中提取项目、模式和输出格式。

如果未提供项目，询问用户：
"您想对哪些项目进行优先级排序？您可以提供列表、引用文件或描述上下文。"

默认模式为 `moscow`。默认输出为 `both`。

### 步骤2：加载优先级排序 Skill

调用 `prioritization` skill 以访问：

- MoSCoW 分类规则
- Kano 模型类别和调查方法
- 加权评分矩阵方法
- 价值 vs Effort 矩阵
- 选择指导（何时使用哪种方法）

### 步骤3：收集项目

收集要优先排序的项目：

**来自内联列表：**

```text
/prioritize "功能A, 功能B, 功能C, 功能D"
```

**来自文件引用：**

```text
/prioritize @backlog.md --mode weighted
```

**来自上下文：**

```text
/prioritize "身份验证模块的 Sprint 规划"
```

对于基于上下文的请求，探索代码库或提出澄清问题以识别项目。

### 步骤4：根据模式执行

#### MoSCoW 模式（默认）

将项目分为四类：

1. **Must Have（必须有）**：关键需求，不可协商
   - 没有这些，解决方案就不可行
   - 核心功能、合规性、安全性

2. **Should Have（应该有）**：重要但不关键
   - 具有显著价值但存在变通方案
   - 下一个迭代的高优先级

3. **Could Have（可以有）**：如果时间/资源允许则理想
   - 锦上添花的功能
   - 增强用户体验

4. **Won't Have（这次不会有）**：明确排除
   - 记录以供将来考虑
   - 有助于管理范围蔓延

对于每个项目，收集干系人对以下方面的输入：

- 业务关键性
- 技术依赖
- 合规要求
- 用户影响

#### Kano 模式（客户满意度）

按满意度影响对项目进行分类：

1. **基本型（Must-Be）**：预期功能
   - 缺失会导致不满意
   - 存在不会增加满意度
   - 示例：登录功能

2. **期望型（One-Dimensional）**：线性满意度
   - 越多 = 满意度越高
   - 越少 = 不满意
   - 示例：页面加载速度

3. **兴奋型（Attractive）**：意外价值
   - 存在会创造兴奋感
   - 缺失不会导致不满意
   - 示例：AI 驱动的建议

4. **无差异型**：无满意度影响
   - 用户不在乎
   - 考虑从范围中移除

5. **反向型**：导致不满意
   - 一些用户主动不喜欢
   - 细分或重新考虑

对于每个项目，考虑：

- 客户期望
- 竞争基准
- 对存在/缺失的情感反应

#### Weighted 模式（多标准）

应用加权标准评分：

##### 步骤 A：定义标准

```markdown
| 标准 | 权重 | 描述 |
|-----------|--------|-------------|
| 业务价值 | 30% | 收入/战略影响 |
| 用户影响 | 25% | 用户体验改进 |
| Effort | 20% | 开发复杂度（反向） |
| 风险 | 15% | 技术/业务风险（反向） |
| 依赖关系 | 10% | 阻塞其他工作 |
```

##### 步骤 B：为每个项目评分

对每个项目的每个标准进行 1-5 分评分。

##### 步骤 C：计算加权分数

```text
分数 = Σ (标准权重 × 项目分数)
```

##### 步骤 D：按总分排名

#### All 模式（比较）

运行所有三种方法并进行比较：

- 识别在不同方法中具有 consistently 优先级的项目
- 突出显示优先级冲突的项目
- 基于综合推荐最终优先级

### 步骤5：生成输出产物

#### YAML 输出

```yaml
prioritization:
  version: "1.0"
  date: "[ISO日期]"
  method: "[moscow|kano|weighted|all]"
  analyst: "ba-orchestrator"

  items:
    - id: "ITEM-1"
      name: "[项目名称]"
      moscow:
        category: "must"
        rationale: "[为什么是必须有]"
      kano:
        category: "basic"
        rationale: "[为什么是预期]"
      weighted:
        scores:
          business_value: 5
          user_impact: 4
          effort: 3
          risk: 2
          dependencies: 4
        total: 3.85
        rank: 1

  summary:
    moscow:
      must: 3
      should: 4
      could: 2
      wont: 1
    kano:
      basic: 2
      performance: 4
      delighter: 2
      indifferent: 1
      reverse: 1
    weighted:
      top_3:
        - "ITEM-1"
        - "ITEM-3"
        - "ITEM-2"

  recommendations:
    immediate: ["ITEM-1", "ITEM-2"]
    next_iteration: ["ITEM-3", "ITEM-4"]
    backlog: ["ITEM-5"]
    remove: ["ITEM-6"]
```

### 步骤6：保存结果

根据格式标志保存输出：

**YAML 文件：**

- `docs/analysis/prioritization.yaml`

**Markdown 文件：**

- `docs/analysis/prioritization.md`

使用 `--dir` 指定自定义输出目录。

### 步骤7：建议后续行动

完成优先级排序后：

```markdown
## 建议的下一步

1. **干系人审查**：与干系人分享优先级以进行验证
2. **Effort 估算**：对高优先级项目使用估算技术
3. **风险分析**：对高优先级、高风险项目使用 `/ba:risk-register`
4. **路线图规划**：将项目排序到交付阶段
5. **能力映射**：使用 `/ba:capability-map` 与能力对齐
```
